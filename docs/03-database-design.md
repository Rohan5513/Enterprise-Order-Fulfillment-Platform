# 03 — Database Design

## 1. Database Strategy

Database-per-service: each service owns its database and is the only one that touches it.

* Services communicate only via REST (sync) and Kafka events (async)
* No cross-service foreign keys, joins, or shared tables
* **Enforced, not just agreed:** every service connects with its own DB user that has rights only on its own database
* Locally: one PostgreSQL instance with six databases and six users; in production these can become separate instances

Trade-offs: no cross-service joins (compose via APIs or events), eventual consistency across services, more operational surface.

---

## 2. Technology

* **PostgreSQL** for all services: ACID transactions, partial indexes, `JSONB`, `SKIP LOCKED`, strong Spring Boot/JPA support
* **Flyway** for migrations (see section 8)

---

| Service              | Database        | Domain tables                                                   | Infrastructure tables                                              |
| -------------------- | --------------- | --------------------------------------------------------------- | ------------------------------------------------------------------ |

| Product Service      | product_db      | products                                                        | none                                                               |

| Notification Service | notification_db| notifications                                                   | processed_events                                                   |

Infrastructure tables are defined in 08 (outbox, processed events) and 10 (idempotency).

## 4. General Rules

* **Primary keys:** `UUID`, generated by the application (UUIDv7 preferred for index locality; v4 acceptable)
* **Timestamps:** `TIMESTAMPTZ NOT NULL DEFAULT now()`, named `created_at` / `updated_at`. `TIMESTAMPTZ` stores an absolute instant; the application works in UTC
* **Table names:** plural, snake_case (`orders` is plural anyway because `order` is a reserved word)
* **Statuses:** `VARCHAR` plus a `CHECK` constraint, not native enums, because changing an enum value in a migration is awkward while altering a `CHECK` is simple
* **Money:** `NUMERIC(12,2)`, never floating point; currency as `CHAR(3)` (ISO 4217, for example `INR`); amounts are `CHECK >= 0`
* **Foreign keys:** only within the same service. Cross-service references are plain IDs
* **Indexes:** create only for known queries. A `UNIQUE` constraint already creates an index, so do not add another on the same columns. In composite indexes, column order follows the query
* **Consistency:** strong within a service, eventual across services
* **Transactions:** local to one service; cross-service flows use the saga in 09

## 5. Schemas

### 5.1 Customer 

```sql
CREATE TABLE customers (
    id            UUID PRIMARY KEY,
    first_name    VARCHAR(100) NOT NULL,
    last_name     VARCHAR(100) NOT NULL,
    email         VARCHAR(255) NOT NULL,
    phone         VARCHAR(20),
    password_hash VARCHAR(255) NOT NULL,
    role          VARCHAR(20)  NOT NULL DEFAULT 'CUSTOMER',
    status        VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT uq_customers_email UNIQUE (email),
    CONSTRAINT ck_customers_email_lower CHECK (email = lower(email)),
    CONSTRAINT ck_customers_role   CHECK (role   IN ('CUSTOMER', 'ADMIN')),
    CONSTRAINT ck_customers_status CHECK (status IN ('ACTIVE', 'INACTIVE', 'BLOCKED'))
);
```

* Email is lowercased by the application and the `CHECK` guarantees it, so uniqueness is case-insensitive
* `password_hash` stores a bcrypt (or Argon2) hash, never the password
* The role is included in the JWT (see 06)

### 5.2 Product 

```sql
CREATE TABLE products (
    id            UUID PRIMARY KEY,
    sku           VARCHAR(50)   NOT NULL,
    name          VARCHAR(200)  NOT NULL,
    description   TEXT,
    category      VARCHAR(100)  NOT NULL,
    price         NUMERIC(12,2) NOT NULL,
    currency_code CHAR(3)       NOT NULL,
    status        VARCHAR(20)   NOT NULL DEFAULT 'ACTIVE',
    created_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT uq_products_sku UNIQUE (sku),
    CONSTRAINT ck_products_price  CHECK (price >= 0),
    CONSTRAINT ck_products_status CHECK (status IN ('ACTIVE', 'INACTIVE'))
);

CREATE INDEX idx_products_category_status ON products (category, status);
```

Stock is not stored here; the Inventory Service owns it.

### 5.3 Order 

```sql
CREATE SEQUENCE order_number_seq START 1;

CREATE TABLE orders (
    id                  UUID PRIMARY KEY,
    order_number        VARCHAR(30)   NOT NULL,
    customer_id         UUID          NOT NULL,
    order_status        VARCHAR(20)   NOT NULL,
    cancellation_reason VARCHAR(30),
    total_amount        NUMERIC(12,2) NOT NULL,
    currency_code       CHAR(3)       NOT NULL,
    version             BIGINT        NOT NULL DEFAULT 0,
    created_at          TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT uq_orders_order_number UNIQUE (order_number),
    CONSTRAINT ck_orders_status CHECK (order_status IN
        ('CREATED', 'PAYMENT_PENDING', 'CONFIRMED', 'CANCELLED')),
    CONSTRAINT ck_orders_reason CHECK (cancellation_reason IS NULL OR cancellation_reason IN
        ('OUT_OF_STOCK', 'PAYMENT_FAILED', 'TIMEOUT', 'CUSTOMER_REQUEST')),
    CONSTRAINT ck_orders_cancelled_reason
        CHECK ((order_status = 'CANCELLED') = (cancellation_reason IS NOT NULL)),
    CONSTRAINT ck_orders_total CHECK (total_amount >= 0)
);

CREATE INDEX idx_orders_customer_created ON orders (customer_id, created_at DESC);

-- Used by the timeout sweeper (09 §8); only indexes rows that can time out
CREATE INDEX idx_orders_stuck ON orders (order_status, updated_at)
    WHERE order_status IN ('CREATED', 'PAYMENT_PENDING');

CREATE TABLE order_items (
    id          UUID PRIMARY KEY,
    order_id    UUID          NOT NULL,
    product_id  UUID          NOT NULL,
    quantity    INT           NOT NULL,
    unit_price  NUMERIC(12,2) NOT NULL,
    total_price NUMERIC(12,2) NOT NULL,
    CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders (id),
    CONSTRAINT uq_order_items_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_order_items_quantity CHECK (quantity > 0),
    CONSTRAINT ck_order_items_total CHECK (total_price = unit_price * quantity)
);

CREATE TABLE order_status_history (
    id            UUID PRIMARY KEY,
    order_id      UUID        NOT NULL,
    from_status   VARCHAR(20),
    to_status     VARCHAR(20) NOT NULL,
    trigger_event VARCHAR(50) NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_order_status_history_order FOREIGN KEY (order_id) REFERENCES orders (id)
);

CREATE INDEX idx_order_status_history_order ON order_status_history (order_id, created_at);
```

Design notes:

* `order_number` is built from the sequence, for example `ORD-2026-00000001`. Sequences can have gaps after rollbacks; that is acceptable for display numbers
* `version` implements optimistic locking so two handlers cannot overwrite each other (09 §7)
* The `CHECK` on `cancellation_reason` ties it to the `CANCELLED` status, so an inconsistent row cannot be saved
* Prices in `order_items` are a snapshot from order time
* `UNIQUE (order_id, product_id)` also serves lookups by `order_id`, so no separate index is needed
* Every status change also inserts an `order_status_history` row in the same transaction (this becomes the UI timeline)
* `customer_id` and `product_id` are IDs only, with no foreign key across services

### 5.4 Inventory 

```sql
CREATE TABLE inventory (
    id                 UUID PRIMARY KEY,
    product_id         UUID        NOT NULL,
    available_quantity INT         NOT NULL,
    reserved_quantity  INT         NOT NULL DEFAULT 0,
    version            BIGINT      NOT NULL DEFAULT 0,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_inventory_product UNIQUE (product_id),
    CONSTRAINT ck_inventory_available CHECK (available_quantity >= 0),
    CONSTRAINT ck_inventory_reserved  CHECK (reserved_quantity  >= 0)
);

CREATE TABLE inventory_reservations (
    id         UUID PRIMARY KEY,
    order_id   UUID        NOT NULL,
    product_id UUID        NOT NULL,
    quantity   INT         NOT NULL,
    status     VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_reservations_order_product UNIQUE (order_id, product_id),
    CONSTRAINT ck_reservations_quantity CHECK (quantity > 0),
    CONSTRAINT ck_reservations_status CHECK (status IN ('ACTIVE', 'COMMITTED', 'RELEASED'))
);
```

**Meaning of the counters (invariants):**

* `available_quantity`: units that can be sold right now (already excludes reserved units)
* `reserved_quantity`: units held for orders that are not yet confirmed
* Units physically in the warehouse = `available + reserved`

| Operation | Effect on `inventory`                              | Reservation status  |
| --------- | -------------------------------------------------- | ------------------- |
| Reserve   | `available -= n`, `reserved += n`                  | `ACTIVE`            |
| Release   | `available += n`, `reserved -= n`                  | `ACTIVE -> RELEASED`|
| Commit    | `reserved -= n` (units are sold and leave stock)   | `ACTIVE -> COMMITTED`|

**Why a reservations table:** counters alone cannot tell which order holds which stock, so a duplicate release event would release twice. Each order's reservation row makes reserve, release, and commit idempotent: only an `ACTIVE` row can be released or committed.

**Timeouts:** the Order Service sweeper cancels stuck orders, which triggers `OrderCancelled` and therefore a release. Reservation expiry inside Inventory is a possible future safety net, not a second mechanism today.

### 5.5 Payment 

```sql
CREATE TABLE payments (
    id                UUID PRIMARY KEY,
    order_id          UUID          NOT NULL,
    attempt_no        INT           NOT NULL DEFAULT 1,
    payment_reference VARCHAR(100),
    amount            NUMERIC(12,2) NOT NULL,
    currency_code     CHAR(3)       NOT NULL,
    payment_status    VARCHAR(20)   NOT NULL,
    payment_method    VARCHAR(50),
    failure_reason    VARCHAR(200),
    refunded_at       TIMESTAMPTZ,
    created_at        TIMESTAMPTZ   NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT uq_payments_order_attempt UNIQUE (order_id, attempt_no),
    CONSTRAINT ck_payments_amount CHECK (amount > 0),
    CONSTRAINT ck_payments_status CHECK (payment_status IN
        ('PENDING', 'SUCCESS', 'FAILED', 'TIMEOUT', 'REFUNDED'))
);

-- Used by reconciliation: find payments whose outcome is still unknown
CREATE INDEX idx_payments_unresolved ON payments (updated_at)
    WHERE payment_status IN ('PENDING', 'TIMEOUT');
```

* A row is created as `PENDING` **before** calling the provider, so a crash mid-call leaves evidence
* The provider call uses the idempotency key `<order_id>:<attempt_no>`, so a retry can never charge twice
* `TIMEOUT` means "unknown outcome": a reconciliation job asks the provider for the real result
* `REFUNDED` plus `refunded_at` cover the late-payment refund from 09

### 5.6 Notification 

```sql
CREATE TABLE notifications (
    id          UUID PRIMARY KEY,
    order_id    UUID        NOT NULL,
    customer_id UUID        NOT NULL,
    type        VARCHAR(50) NOT NULL,
    channel     VARCHAR(20) NOT NULL DEFAULT 'SIMULATED',
    status      VARCHAR(20) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_notifications_order_type UNIQUE (order_id, type),
    CONSTRAINT ck_notifications_type CHECK (type IN
        ('ORDER_CREATED', 'ORDER_CONFIRMED', 'ORDER_CANCELLED', 'PAYMENT_REFUNDED')),
    CONSTRAINT ck_notifications_status CHECK (status IN ('SENT', 'FAILED'))
);
```

`UNIQUE (order_id, type)` means a customer can never receive the same notification twice, even if dedupe somehow fails.

## 6. Inventory Concurrency (decision)

Three options were considered: optimistic locking, pessimistic locking (`SELECT ... FOR UPDATE`), and an atomic conditional update.

**Chosen: atomic conditional update.**

```sql
UPDATE inventory
SET available_quantity = available_quantity - :qty,
    reserved_quantity  = reserved_quantity  + :qty,
    version            = version + 1,
    updated_at         = now()
WHERE product_id = :productId
  AND available_quantity >= :qty;
-- 0 rows updated  =>  insufficient stock
```

Why: one statement, no read-then-write gap, no explicit locks held across application code, and no retry storms when many orders hit the same hot product (which optimistic locking would cause). The row lock is held only for the statement.

Rules for multi-item orders:

* All items in **one** local transaction: all reserved or none
* Update inventory rows in ascending `product_id` order, so two orders cannot deadlock on each other
* On failure, roll back to a savepoint, then in the same transaction record the dedupe row and the `InventoryReservationFailed` outbox event
* The `CHECK (available_quantity >= 0)` is the last line of defence, not the primary mechanism
* `version` is used for optimistic locking on admin operations (see 06)

Proof to build later: a test that fires 100 parallel orders at 10 units of stock and asserts exactly 10 succeed and `available_quantity = 0`.

## 7. What Can Go Wrong

* Duplicate operations: covered by idempotency (10)
* Lost events: covered by the outbox (08)
* Overselling: atomic update plus `CHECK`
* Reservation never released: covered by cancellation flow, sweeper, and release idempotency
* Payment outcome unknown: `PENDING/TIMEOUT` plus reconciliation
* Slow queries as data grows: indexes are tied to known queries; add `EXPLAIN` checks in the load test

## 8. Migrations

Flyway, one migration folder per service (`src/main/resources/db/migration`).

* Naming: `V1__create_customers_table.sql`, `V2__...`
* **Never edit a migration that has been applied**; add a new version
* Hibernate runs with `ddl-auto=validate`, never `update`, so Flyway is the only thing that changes the schema
* Changes are backward-compatible where possible (add nullable column, backfill, then enforce), so a rolling deploy works
* Migrations run automatically at startup
