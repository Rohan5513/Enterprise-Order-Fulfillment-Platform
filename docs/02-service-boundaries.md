# Service Boundaries

## 1. Purpose

The Enterprise Order & Fulfillment Platform (EOFP) is designed as a set of independently deployable services. Each service owns a specific business capability and its associated data.

The primary goal of defining service boundaries is to maintain clear responsibilities, reduce coupling, and allow individual services to evolve independently.

## 2. Service Overview

| Service              | Responsibility                                               | Owns Data                      |
| -------------------- | ------------------------------------------------------------ | ------------------------------ |
| Customer Service     | Customer registration, authentication and profile management | Customer                       |
| Product Service      | Product catalog and product information                      | Product                        |
| Order Service        | Order creation and order lifecycle management                | Order, OrderItem               |
| Inventory Service    | Product stock and inventory reservation                      | Inventory                      |
| Payment Service      | Payment processing and payment status                        | Payment                        |
| Notification Service | Customer notifications                                       | Notification data, if required |

## 3. Customer Service

### Responsibility

The Customer Service manages customer-related information.

### Owned Data

* Customer ID
* First name
* Last name
* Email
* Phone
* Password hash
* Customer status
* Created timestamp
* Updated timestamp

The Customer Service is the only service responsible for modifying customer data.

---

## 4. Product Service

### Responsibility

The Product Service manages the product catalog.

### Owned Data

* Product ID
* SKU
* Name
* Description
* Category
* Price
* Currency
* Product status
* Created timestamp
* Updated timestamp

Product availability/stock is not owned by the Product Service. Inventory is managed by the Inventory Service.

---

## 5. Order Service

### Responsibility

The Order Service is responsible for creating and managing customer orders.

### Owned Data

#### Order

* Order ID
* Order number
* Customer ID
* Order status
* Total amount
* Currency
* Created timestamp
* Updated timestamp

#### OrderItem

* Order item ID
* Order ID
* Product ID
* Quantity
* Unit price
* Total price

The Order Service stores customer and product identifiers but does not own customer or product data.

---

## 6. Inventory Service

### Responsibility

The Inventory Service manages product stock.

### Owned Data

* Inventory ID
* Product ID
* Available quantity
* Reserved quantity
* Updated timestamp

The Inventory Service is responsible for reserving and releasing inventory.

---

## 7. Payment Service

### Responsibility

The Payment Service manages payment processing and payment status.

### Owned Data

* Payment ID
* Order ID
* Payment reference
* Amount
* Currency
* Payment status
* Payment method
* Created timestamp
* Updated timestamp

Initially, the project will use a mock payment provider so that payment success and failure scenarios can be tested safely.

---

## 8. Notification Service

### Responsibility

The Notification Service handles notifications generated by business events.

Examples include:

* Order created
* Payment successful
* Payment failed
* Order confirmed
* Order cancelled

Initially, notification delivery will be simulated.

---

## 9. Database Ownership Principle

Each service owns its own data.

Services must not directly access another service's database.

For example:

```text
Order Service
      |
      X
      |
Customer Database
```

This direct database access is not allowed.

Instead:

```text
Order Service
      |
      | API / Event
      ▼
Customer Service
      |
      ▼
Customer Database
```

This maintains service ownership and reduces database-level coupling.

---

## 10. Service Communication

The platform will use two primary communication mechanisms.

### Synchronous communication

REST APIs will be used when an immediate response is required.

Example:

```text
Angular
   |
   ▼
API Gateway
   |
   ▼
Product Service
   |
   ▼
Product Database
```

### Asynchronous communication

Kafka events will be used for asynchronous business workflows.

Example:

```text
Order Service
      |
      | OrderCreated
      ▼
    Kafka
      |
      +------> Inventory Service
      |
      +------> Payment Service
      |
      +------> Notification Service
```

The exact Kafka topics and event contracts will be defined in a later design phase.

---

## 11. Initial Service Dependency Principles

The following principles will guide the architecture:

1. A service owns its business data.
2. Services do not directly access another service's database.
3. REST is used for synchronous request/response communication.
4. Kafka is used for asynchronous business events.
5. Service boundaries should be based on business capabilities rather than database tables.
6. The architecture should allow individual services to evolve independently.
